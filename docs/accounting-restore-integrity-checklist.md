## A. 復旧前：既存資料を保護する

- [ ] 代表が障害原因・復旧対象・復旧点/RPO・許容停止時間/RTO・担当者・中止条件を承認。
- [ ] 稼働DB絶対パス、参照する全アプリ/ワーカー/手動ツール、コードcommit、設定/社員定義の指紋、DB系統IDを特定。
- [ ] 独立状態で会計停止を先に永続化し、全writer/reader/自動処理を停止。署名/最新head取得失敗なら中止。
- [ ] 現在DB・WAL/SHM/journal・監査・外部状態を証拠保全。稼働中のDB本体だけを単純コピーしない。WALを削除して整合したように見せない。
- [ ] SQLite正式backup APIで、停止確認後、新規の退避先へ保存。既存backup・validation・repair-trialは一切上書きしない。既存準備補助の停止/WAL条件に合わなければ止める。
- [ ] バックアップごとに生成日時/元系統/コード/schema版/世代/size/SHA-256/独立台帳headをmanifestへ記録し、別権限・別障害領域で保護。ハッシュ一致だけで真正性や新しさを判定しない。
- [ ] 破損で現在DBを読めない項目は「未確認」とし、完全保持を保証しない。ログや証拠を無理に修正しない。

## B. 隔離先での検証（本番参照先の切替は別承認）

- [ ] 新しい隔離パスにだけSQLite backup APIで候補を作る。元DB/backupは入力として変更しない。試験DBを本番へコピー・置換しない。
- [ ] integrity_check全結果=ok、foreign_key_check=0、接続foreign_keys=ON。エラー時は停止して別修復計画へ。bf_profiles不足の既知28件も隠さない。
- [ ] sqlite_masterのtable/index/view/trigger/SQL、table_info、PK/NOT NULL/UNIQUE、foreign_key_list、index_list/index_info、user_version、既存migration記録とコード版の整合を確認。
- [ ] 全テーブルの行数、PK/複合キー集合、NULL/重複、各行の型を含む内容、多重集合の差分を比較。キーのない表も行ハッシュ＋重複数で比較。順序や集計値一致だけで同一扱いしない。
- [ ] バックアップ→候補のschema/全行が一致することを確認。今回はschema導入やbf_profiles追加を復元と混ぜない。
- [ ] 復旧直前DB→候補の差分は別に列挙。バックアップより後の行/変更/削除/監査を全部抽出し、喪失・再投入可否・保全先・代表判断を記録。過去DBは最新DBと同一でなくて当然だが、無差分と誤報しない。
- [ ] 既存事業本体、AI01〜28定義ファイル指紋、担当のbusiness_id/agent/role/permissions/active/revision、会計台帳/顧客情報、全監査を重点比較。バックアップ以後の担当差分も勝手に戻してよいとはしない。
- [ ] acct_task_policies/reads/handles/eventsも全行保存。分類マーカー削除や旧承認一括UPDATEはしない。
- [ ] 外部head照合と停止状態を確認。新epoch発行失敗なら旧epochを流用しない。

## C. 途中失敗とロールバック

- [ ] コピー/manifest/履歴照合失敗：隔離候補を不採用とし、本番参照は切り替えない。元DB・backup・現行監査は不変。失敗候補と理由を保全し、自動削除しない。
- [ ] 正式schema移行は別工程・同一SQLite transactionのDDL＋版記録で戻す。executescriptを原子性の根拠にしない。
- [ ] 将来の切替途中失敗：全プロセスを停止したまま、独立ゲートclosedを維持。どのDB/世代がactiveか不明なら一切再開しない。
- [ ] 旧DBへ戻す判断も独立台帳の失効・世代を巻き戻さない。旧アプリの広域finance fallbackやops.restoreの副作用を使って回避しない。
- [ ] 再試行は新候補/新決定IDで証拠を残す。候補を実DBに上書きするコマンドは本成果物に含めない。

## D. 復旧結果と再開

- [ ] 成否/段階/復旧ID/actor/時刻/前後manifest digest/独立head/差分件数/未確認項目/欠落範囲/停止継続を、DB巻戻しに含まれない監査へ記録。機密内容はログへ出さない。
- [ ] DB整合性回復の確認を代表が承認してから、会計再承認を別申請。
- [ ] 会計停止のまま代表が新規policyを対象事業・社員・項目・期間・目的・expiry・taskごとに承認。旧policy復活/一括承認は禁止。
- [ ] 新receiptありでも現在の担当/role/事業/期限/取消と独立世代を毎回再検査。AI04拒否、他事業拒否、無承認拒否、取消後拒否、全28役職、旧3経路＋専用経路を再確認。
- [ ] 非会計業務と代表機能の動作を確認し、会計が止まる業務を明示。権限自動追加で再開しない。
- [ ] Windows追加テスト、既存skipの名称/理由、障害演習、運用者の手順確認が完了するまでは本番再開を承認しない。
