# accounting-access-v1：互換性調査と段階移行

基点925db46で静的検索と合成の実経路検証を実施。外部クライアントとWindowsのローカル追加スクリプトは未確認です。アプリ本体・既存ブラウザスクリプトは今回変更していません。

今回の追加テストで旧ブラウザの呼び出し準備を再現すると403、明示的な合成承認と関連付け後は200になることを確認します。HTTP本体の拒否を緩める修正はしません。

リポジトリの実行コード内で会計read_for_aiを広く呼ぶUIは見つからず、主な実接続はbusiness_operations.for_task→HTTPです。business_foundation_demoは非会計メタデータを使用します。ただし外部コードがないとは断定できません。

## 新契約の扱い

- 旧データの復活や、未知のキーをそのままテンプレートへ展開する方法は使わない。
- dataは通常の限定辞書か、advertising/termsの確認済み数値レコード配列。区分別に型と許可キーを検証する。
- nullは欠測/基準未確認を意味し得るため0へ置換しない。円とUSD、旧台帳とSCM、実績と予測を無断で合算しない。
- versionヘッダー/本文、source、period、limitationsを確認する。証憑や銀行照合済みの会計として誤表示しない。
- 403は再承認や担当確認へ案内する。旧経路再試行やfinance_read自動追加で回避しない。400は要求/契約確認、503等は安全停止とする。
- 代表用の人間集計は別の信頼境界。AIへ代表資格情報を渡して互換性を維持しない。

## 段階的な移行案

1. 利用側一覧と所有者、期待キー/型、目的/期間をローカルで収集。未確認の外部利用側があれば限定導入を保留する。
2. 同じ合成データで旧計算と新dataの同じ許可項目だけを比較する。旧レスポンス全体をAIへ渡す二重実行モードは作らない。
3. 代表画面、非会計業務、ポリシー未準備時の拒否、会計報告の停止理由を検証する。
4. ブラウザfixtureを更新し、承認前403/後200、返却項目、なりすまし400、他事業403を実ブラウザで再確認する。外部ブラウザ要求は遮断する。
5. 専用報告UIと資料分類を接続してから、対象事業・社員・タスクを限定した導入演習へ進む。
6. 代表が契約変更、停止する業務、再開条件を承認した後に本番計画を確定する。現在は配備しない。

本番の旧レスポンスを復活させる互換アダプターは作りません。許可済みdataの同義項目を局所的に表示名へ変換する場合も、項目・事業・期間・利用者の権限を拡張しないレビューが必要です。
