# 第20段階向け画面・API契約と受入条件（実装準備資料）

これは代表の第19段階指示に基づく画面実装仕様の準備であり、第20段階の画面実装完了を意味しない。第20段階の「代表が新規事業を追加し、既存28人を事業別に割り当てられる」という完成条件を保持する。第13.5段階の商品計画等、他の未提示範囲を追加しない。

## A. 新規事業追加・編集・停止

1. 代表のみ「＋ 新規事業追加」を操作可能にする。事業担当者には担当事業の確認導線だけを表示。
2. 事業名・事業内容・カテゴリを入力。開始日は任意。既存分類にない事業は汎用otherと自由カテゴリを使用し、既存事業名を自動変更/統合しない。
3. サーバーのpreviewで不正入力・正規化した重複名を検証。ここではDBに事業・変更案を保存しない。
4. 入力値と準備中/担当なし/価格・目標未設定等の初期状態を確認してprepare。代表が変更内容を承認しても事業登録は未適用。
5. 別のapply操作で登録し、応答後に一覧を再取得して新しい管理IDを表示する。失敗時に成功表示しない。
6. 編集・停止/再開も同じ確認/承認/適用フロー。停止はデータ削除ではない。提供中へ変更する場合は代表の提供確認が必須。

入力必須/任意フィールド、事業分類・状態はGETのcontract.operation_fields/business_kinds/business_statesから取得できる。未確認の料金・資格・公式条件を初期値として捏造しない。

## B. 既存28人の事業別担当割当

1. 権限のある事業を選び、その事業のcontractを取得する。社員ID・役職・既存レビュー担当はサーバーの既存定義を表示し、増員・再生成・改名をしない。
2. 担当の有無・役割補足・対応範囲・権限（business_read/work/finance_read）・有効状態を表示。work/finance_readはbusiness_readが前提。
3. 既存事業に基盤メタデータがなければ、先に代表がカテゴリ等を確認して更新する。カテゴリを推測して自動採用しない。
4. 変更した社員だけをassignまたはassign_manyへ渡す。最大28人、重複ID禁止。未選択社員を自動解除/変更しない。
5. previewの前後差分と影響を確認。独立レビュー担当の割当不足は説明し、自動的に権限を付与しない。旧事業の互換モードも自動切替せず、全体の厳密化が必要なら既存BusinessFoundation.get/enforce（代表のchecked確認・現在タスクの担当検証付き）を利用する。
6. 一括変更は1つの変更案として承認し、別applyで全件成功または全件取消。途中成功だけを画面へ反映しない。
7. 解除はunassignまたは既存担当のactive=falseとして論理停止する。過去の成果物・顧客・監査・担当履歴を削除しない。兼務先の別事業には影響させない。
8. 担当不在・解除後の業務は第18段階の確認待ち・権限拒否を表示し、無断で別担当へ引き継がない。必要なら既存の同一事業引き継ぎ手順を使う。

## 操作契約

- GET `/business-readiness-data?business=ID`：事業別のcontract、事業メタデータ一覧、変更案、履歴。businessなしは代表専用の全体管理情報。
- POST `/business-readiness-preview`：kind/business/payload(JSON文字列)/csrf。状態を変更しない事前確認。
- POST `/actions/br_prepare`：上記にkey/nonce。変更案保存のみ。
- POST `/actions/br_decide`：id/decision=approveまたはreject/checked=1/csrf/nonce。承認または却下のみ。
- POST `/actions/br_apply`：id/csrf/nonce。現在も承認内容が有効な場合だけローカル設定適用。

すべて既存のログイン・Origin・CSRFを使用し、変更POSTにはnonceも必要。サーバーの現行ロール/事業権限を検証する。クライアントから社員の権限や承認者を自己申告しても認可しない。POSTの応答は既存画面への303（previewはJSON）。prepare後の変更IDはGETのentry_keyで確認でき、サービス直接呼出しなら戻り値で受け取れる。

承認後に事業・担当等が変わった場合はstaleとして再確認。新しいキーで現在値からプレビューを作り直し、古い承認を自動更新しない。新規登録時に他の事業追加があった場合も一覧の再確認が必要。

## PC・390px幅の表示案

PCは事業選択と一覧/差分を見比べる構成、390px幅は1列の入力・社員カード・差分確認とする。権限の説明と「承認」「適用」を区別し、外部公開・顧客への連絡を行うと誤認させない。細かいデザインは第20段階で検証し、ここで完成済みとしない。

## 第20段階の受入条件

- ボタンから事業入力、事前確認、承認、適用、一覧反映、編集、停止/再開を実ブラウザで操作できる。
- 既存28人の一覧、事業選択、担当選択、役割/権限設定、個別/一括保存、変更、論理解除、兼務状態を操作できる。
- stale、却下、二重クリック、並行更新、途中エラー、権限不足で不正な保存・成功表示がない。
- 解除後の旧タスク・事業外読取/更新が拒否され、無断の顧客共有・送信がない。
- PC/390px幅でレイアウトと操作を検証する。iPhone実機は実機確認をした場合だけ合格と報告する。
- 既存全テスト、DB保持/復旧、事業間分離、同意/承認/監査を維持。公式情報の確認待ちを勝手に解除しない。
- 新機能の実装、本番移行、外部接続の承認は別。実LINE・メール・決済・公開をこの画面保存から起動しない。
