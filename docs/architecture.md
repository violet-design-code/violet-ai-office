## 保存と状態

SQLiteはWAL、外部キー、BEGIN IMMEDIATEを利用。dedupe_keyの一意制約と内容の指紋で同一依頼の再登録を吸収し、異なる内容でのキー再使用は拒否。実行中履歴はタスクごとに1件。複数接続の競合はDBで直列化する。

pending → running → review_pending → completed（内部作業）または approval_pending（対外用途）→ manual_execution_pending / rejected。
レビュー差戻しは changes_requested。修正は新しいキーのタスクとして作成し、旧成果物の承認を流用しない。履歴・成果物・レビュー・承認は各テーブルに保存。イベントログには本文やAPIエラー原文を記録せず定型イベントのみ保存。

claimは原稿等のローカル作業の占有であり、送信許可ではない。成果物は更新APIを設けず承認を成果物IDに固定。decideのactor検査はローカルAPI契約であり本人認証ではない。現段階ではDBにアクセスできる人を信頼する。インターネット公開不可。AI28のpass記録は法的適合性の保証ではない。

## 期限・再試行・予算

実行期限は1〜300秒、試行上限は1〜5回。期限後の成果物は拒否。expireで期限切れを検出して再試行可能にする。失敗のコードは列挙値のみ保存。外部呼出そのものの中断や自動スケジューラは未実装。

費用は整数のmicro USD（1 USD = 1,000,000）。DBの初期予算は既定0。claimで最大費用を事前予約し、競合する予約の合計をDB予算以下に制限。成功・失敗・期限切れ後も予約を保守的に消費扱いとし、自動払い戻しはしない。実請求精算APIは未実装。再初期化しても既存上限を上書きしない。現段階ではAPI呼出や実課金は一切ない。将来は最大トークン・単価・予約上限を呼出側でも強制する。

## 個人情報・監査

タスク本文と成果物は保存される。自動匿名化や秘密情報検出は未実装のため、実顧客名、連絡先、健康情報、APIキーを入力しない。合成データと匿名化資料のみ使用。DBは平文であり暗号化・保存期限・削除運用は本番前の必須課題。CLIはDBを0600、作成ディレクトリを0700にする。秘密は将来環境の安全なバインディングから渡し、プロンプトやログに含めない。

AI28監査では以下を記録する：参照した公式文書URL・版・確認日・対象成果物・問題点・修正・代表判断。

- ベネシード公式規約・ディーラー契約の最新版（代表提供または正規取得した資料を使用）
- 特定商取引法: 消費者庁の法令・ガイドライン、勧誘目的・販売形態・必要表示・禁止勧誘
- 景品表示法: 消費者庁の表示ガイドライン、根拠のない効能・収入・成功実績・紹介報酬の断定禁止、広告表示
- 個人情報保護法: 個人情報保護委員会の法令・ガイドライン、利用目的・同意・最小取得・委託・削除
- 健康美容表現: 必要に応じ薬機法・健康増進法も専門家確認
- 無断連絡・スパム・無断スクレイピング禁止。連絡先の保有だけを同意と扱わない

本段階では公式規約・法令の実査や法的判断は未完了。確認資料と必要時の専門家確認なしに公開・送信しない。第3段階以降は監査チェックリストを機械的な必須ゲートにする。

## 既存LINEシステムとの将来の連携契約（提案・未接続）

既存側を配信同意・停止・再同意・予約時停止の唯一の正とする。Officeは既存DBを直接読み書きせず、将来許可されたAPIまたは代表の手動エクスポートに限定する。原稿・配信予定の提案と実際の配信命令を分離する。

連携時に必要な非秘密メタデータは、相関ID、OfficeタスクID、成果物ID/ハッシュ、承認ID、有効期限、匿名の宛先参照ID、目的、冪等キー。生のLINEユーザーID・連絡先・アクセストークンを原稿生成に渡さない。既存側は送信直前に承認対象・同意・停止・予約状態を再検査し、拒否を最優先する。Officeでの承認は停止解除・再同意を意味しない。

API有無・イベント仕様・認証方式は未確認。架空のエンドポイントを用意せず、合意後に専用アダプターを追加する。Webhookは署名検証、イベントID重複排除、順序逆転対策を行う。タイムアウト後は結果不明として照会・手動確認し、同じ連絡を盲目的に再送しない。既存データの移行・削除・スキーマ変更は本フェーズの対象外。
