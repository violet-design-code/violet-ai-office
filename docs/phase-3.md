## 調査と監査の正確な範囲

市場調査は公開情報の参照候補・仮説・検証計画の作成まで。ネットワーク取得は一切していないため確認済み市場事実は0件。record_source APIで、利用許諾を確認して人が取得した公開資料のURL・抜粋・根拠参照・日時を登録できる。reported_factは「人が事実として報告した記述」であり独立検証済みを意味しない。hypothesisと区別し、自動的に原稿へ事実として転載しない。

AI28処理は実際にルール照合を実行するが、限定した禁止語の検出であり網羅的な勧誘・効能判定ではない。誤字脱字、出典、法令、公式規約は人の確認が必要。法的適合性は保証しない。公式規約のURLや紹介報酬を推測で作らない。

## 承認と版管理

下書き → 品質確認（イベント記録）→ 代表承認待ち → 承認済み → 公開済み（代表による手動実施記録のみ）。禁止語検出時は修正必要。未確認でも承認待ちには並ぶが、事実・誤字脱字・各法令・規約・同意・リンク等の全確認記録がない限りapproveは拒否する。テスト以外で確認記録や承認を代行していない。

修正は新しい版を作り、旧版をsupersededにする。旧承認は新原稿へ流用不可。監査前の新原稿も承認不可。承認はcontent_eventsに本文ハッシュと代表ロールで記録。公開操作はなく、publicationは代表が別途手動実施した事実の証跡を記録するだけ。

第2段階のtasks/reviewsと原稿承認は別の記録。キャンペーン担当タスクはテンプレート結果を生成後review_pendingとなり、人のレビューを偽って登録しない。AI01の処理は件数・参照一覧・注意点の統括確認であり、法令レビューの合格ではない。原稿の外部利用可否はcontent_versions/content_auditsの専用フローが正で、旧decideを呼んでも原稿は承認されない。

## 安全性と再試行

キーと入力指紋による冪等性。キャンペーン・子タスク・原稿・監査を同一トランザクションで保存し、途中失敗はロールバック。修正後の同じ入力で再試行できる。開始日は再実行時も同じ日を明示する。外部APIも自動再送もない。失敗履歴はCLIで定型コードのみ保存する。

実利用料0、ネットワーク呼出0、有料APIなし。テンプレート処理の予算予約は0。将来の課金実行器は既存Storeの予算予約に加えて、料金・トークン上限と実タイムアウトを強制する必要がある。本段階のコードは有料実行器を持たない。

入力のメール・電話・一部トークン形式は拒否するが、一般的な秘密検出・匿名化を保証しない。合成・匿名化データのみ。DBとHTMLは平文でローカル専用、本人認証は未実装。CLIはumask077とDB0600、HTMLの文字列はエスケープする。既存の出力ファイルは上書きしない。
