# VIOLET AI OFFICE 運用・障害復旧マニュアル

## 運用範囲

現版はPC内限定のローカル管理・ルール割当・固定テンプレート・モック連携。実LLM・LINE・SNS・予約/カレンダー・外部CRMは未接続。匿名/合成データで検証する。LAN/インターネットに公開しない。別リポジトリの既存LINEを操作・停止・移行しない。

## 初回起動とPCのデスクトップ

Python 3.12以上でリポジトリへ移動する。実行時の第三者ライブラリは不要。

```sh
python3 -m violet_office.web init
python3 -m violet_office.web serve --open-browser
```

Windowsはpython3の代わりに `py -3`。initで代表/閲覧者に別々の12文字以上のパスワードを対話入力する。ユーザー名はrepresentative / viewer。既存アカウントは上書きしない。

ブラウザのアドレス欄は `http://127.0.0.1:8765/` 。クラウド側のlocalhostを手元PCから開けるという意味ではなく、PC上でサーバーを起動する。初回設定後、Windowsはscripts/start_office.batのショートカットをデスクトップに置き、Mac/Linuxはscripts/start_office.shをOSのランチャーに登録する。スクリプトはPC内のブラウザだけを開く。Windows/macOS実機の動作は未検証。

## 環境変数と認証情報

.env.exampleは名前の一覧であり自動読込しない。実キーをソース、コマンド引数、シェル履歴、原稿、プロンプト、ログに入れない。現在のWeb認証はDBのsalt付きパスワードハッシュで管理し、LINE等のキーは起動に不要。

| 設定 | 現版での用途 | 将来の注意 |
| --- | --- | --- |
| INTEGRATION_MODE | mock/local/testのみ。production等はWeb起動を拒否 | 値を変えてもライブ接続は有効化しない |
| LINE_CHANNEL_SECRET | モックWebhookのHMAC検証用に合成値を使用 | 実Webhookでは生の署名鍵が必要。プロキシ用APIトークンと区別 |
| LINE_CHANNEL_ACCESS_TOKEN | 未使用 | Messaging API、送信権限と宛先・期限を正規に確認 |
| LINE_EXPECTED_DESTINATION | モックチャネルの宛先識別子 | 本番の正規チャネルと照合 |
| CRM_PSEUDONYM_KEY | モック顧客IDの仮名化鍵 | 32文字以上、暗号化保管、ローテーション/対応移行設計が必要 |
| INTEGRATION_ADMIN_TOKEN / VIEWER_TOKEN / SESSION_TOKEN | 第4段階ローカルCLIの代表/閲覧用 | Webのパスワードとは別。異なる32文字以上を安全な環境から注入 |
| META_ACCESS_TOKEN / アカウント・ページID | 未使用 | 採用するLogin方式、正規権限、App Review、期限の確認後に設定 |
| BOOKING_PROVIDER | 未選定 | サービス選定後にOAuth等の認証方式を確定 |
| AIモデルAPI認証 | 未選定・未定義 | プロバイダー、予算、利用条件、安全なバインディングを決めてから追加 |

設定値をチャットで送らない。共有PCやCIのシークレット保管庫を使用する場合は適用範囲を限定する。安全な注入方式が決まるまで本番キーを入れない。

## 毎日の代表操作

1. 社長室の要対応通知と監視画面を確認する。モック成功を本番成功と扱わない。
2. 28人の役割・ローカル作業状態を確認。5部門長の管理は担当関係の集計で、自律的な管理AIは未実装。
3. 指示画面で担当を割り当てる。日本語はキーワード方式。知らない依頼は要確認として扱う。
4. 手動作業を開始し、匿名化した成果物を登録。別担当の確認事実を記録してから代表承認する。
5. 承認センターで原稿版と根拠を読む。法令確認はlegal-review.mdに従う。未確認を確認済みと入力しない。
6. 経費画面で推定/確定/モックを分け、予算と予約残高を確認。請求自動取得は未計測。同じ費用の推定/確定/予約は保守的に重複計上され得るため照合する。
7. バックアップを取得し、暗号化されたアクセス制限付き保管先で保持する。外部への複製は別途承認を得る。

## 承認と停止

原稿は下書き→品質チェック→代表承認待ち。全法令・規約・根拠の確認記録が必要。承認/修正依頼/却下に日時と担当を残す。原稿修正は新しい版で再監査する。

承認後も実送信・公開・実予約確定しない。Webに送信実行ルートはない。第4段階のdispatch_mockは合成APIを呼ぶ試験だけで、代表の実際の本番承認ではない。

画面の一時停止はローカルタスク状態の停止。外部プロセスや実LINE配信を止める機能ではない。既存LINEの停止・再同意・予約時停止は既存側の正規手順を守る。

## 障害別の対応

| 事象 | 対応 |
| --- | --- |
| ログイン不可 | ユーザー名・パスワード確認。10分の試行上限と30分の無操作期限を確認。DBを消さない。全認証情報を失った場合のOS管理者復旧は別作業 |
| CSRF/Originエラー | 正規のPC内アドレスから再ログイン。Cookieを他サイトに送らない。検証を無効化しない |
| 429/接続過多 | 最大180要求/分、同時16接続。60秒以上の間隔を空ける。不明なPC内プロセスを調査 |
| タスク失敗 | 監視画面の固定エラーコード、担当、期限を確認。原因修正後に代表が新規試行を依頼。自動試行上限は1〜5回 |
| API未受付（モック） | 承認・状態を再確認し、バックオフ後に最大3回。未受付と確認できる場合だけ |
| API結果不明 | 自動再送しない。手動照合待ちとして枠/配信を抑止。実サービスでは正規の結果照会が必要だが現版は未接続 |
| 予約変更/取消 | 代表承認をやり直す。取消後もステップ配信を勝手に再開しない |
| 予算到達 | 新しい有料予約は拒否。原則調査を優先し、上限を無条件に引き上げない。無料のローカル作業は別 |
| DB異常 | サーバーを止め、原本を保全。下記health/backup/restoreで別ファイル検証。元DBにreset/drop/deleteしない |
| 秘密漏えい疑い | 原稿/ログへの転載や外部送信を止め、対象認証を正規の保管元で失効/再発行。証跡保全と個人情報対応を代表が判断 |

エラー通知は管理画面内のみ。メール/LINE/Slackへの通知は未接続で送らない。エラー文の原文やトークンをチャットに貼らない。

## バックアップ（既存DBを変更しない）

整合性を確認する。業務を止めた状態を推奨するが、SQLite backup APIはWALのコミット済みデータも扱える。単純な.dbファイルのコピーでWALを落とさない。

```sh
python3 -m violet_office.ops health --db var/office.sqlite3
python3 -m violet_office.ops backup --db var/office.sqlite3 --output var/backups/office-YYYYMMDD-HHMM.sqlite3
```

新しいスナップショットと `.backup.json` を作成。既存出力は上書きしない。整合性、外部キー、依存循環、SHA256を検証。コピーは原則30秒上限。manifestは暗号署名ではなくチェックサムなので、信頼できる保管先を使う。ファイルは平文であり機密性を保証しない。OS暗号化/暗号化バックアップとアクセス制限を本番前に用意する。DB・manifest・.envをGitに追加しない。

バックアップ保持日数・世代数は法的根拠と事業上の必要性を代表が決める。自動スケジュール・自動世代削除は未実装。本人データの削除方針はバックアップにも適用する。

## 別ファイルへの復元・復旧

```sh
python3 -m violet_office.ops restore --db var/backups/office-YYYYMMDD-HHMM.sqlite3 --output var/recovery/office-restore-YYYYMMDD.sqlite3
python3 -m violet_office.ops health --db var/recovery/office-restore-YYYYMMDD.sqlite3
python3 -m violet_office.web serve --db var/recovery/office-restore-YYYYMMDD.sqlite3 --port 8766
```

必ず新規出力へ復元。原本・既存の復元先を上書きしない。ログインセッションを失効し、実行中タスクを一時停止、未完了外部操作を照合待ち、予定配信をrecovery_hold、承認済み原稿を再承認待ちにする。いずれも新しい復元コピーのみで、元DB・バックアップは変更しない。

復元前のセッションは使用できないため通常ログインし直す。タスク/原稿/予約/停止/同意/経費の件数・根拠・未確定操作を代表が確認する。結果不明操作を新キーで再送して回避しない。旧来の実行器や本番LINEへの照合機能は未接続なので、復元だけで本番稼働に進めない。

稼働DBの切替は、検証後に代表が新規ファイルを--dbで明示して起動する。旧DBを削除/置換しない。復元の自動再開・旧アプリの自動起動も行わない。

## 保存期限・削除計画

```sh
python3 -m violet_office.ops retention-plan --db var/office.sqlite3
```

期限切れ件数と検討事項だけを出力し、削除しない。顧客の暫定保持期限は取得から90日。目的、法令、委託、停止/同意履歴、監査、重複防止、バックアップの保持を代表が確定する。本番データの自動パージは未実装。本人請求に対応する際は本人確認・範囲・第三者提供・既存LINE側を照合し、代表の明示承認後に別途削除を実施する。

## システム停止

サーバーを起動したターミナルでCtrl+C。デスクトップ起動でも元のターミナルを確認する。停止後にバックアップを取得する。別リポジトリのLINE運用はこのサーバーとは別で、この操作で止まると想定しない。強制終了後のrunningは監視で確認し、検証後に手動停止/再依頼する。

## 定期検証

```sh
python3 -m unittest discover -v
python3 -m violet_office.validation --output /tmp/violet-validation-new.json
```

validationは現在のソース指紋・実行したテストID・合否・依存棚卸し・本番判定を保存する。既存ファイルを上書きしない。最新CVE照合や本番疎通を代行しない。任意のブラウザ検証はPlaywright/Chromiumを導入したテスト環境でのみ実行する。

```sh
python3 -m tests.browser_smoke --output-dir /tmp/violet-browser-new
```

一時DB・合成アカウントで、ローカル以外のブラウザ通信を遮断する。実顧客DBや本番キーでテストしない。

## 第7段階の定期業務

目標・日別計測・日週月の計画/報告を追加した。初期停止、手動有効化、明示tick/watchのみ。詳細はphase-7.md。スケジュール変更は停止後に設定版を更新する。失敗時は自動停止、代表再開後の最大3試行。実LLM/外部送信はない。

復元ではgrowthスケジュールをすべてrecovery_hold、実行中レポートを隔離し、承認済み計画と提案を再承認待ちにする。バックアップ前の承認を使って勝手に新規タスクを開始しない。

## 知識・フィードバック・改善の運用

「知識・改善」では公開/非個人情報だけを登録する。出典・共有先・業務・期限を明示し、指導と知識を別々に承認。旧版や期限切れは利用停止になり、更新は新版の作成→承認が必要。適用済み改善でも参照元撤回/期限切れで元の文章へ戻る。誤ったスタイルは「適用を停止」を使用し、履歴を消さない。

評価は役割/業務/期間/母数を揃えて確認し、評価不能を低能力と解釈しない。機械チェック通過は法令適合の保証ではない。原稿の承認/公開条件は従来どおり別操作。バックアップには知識/指導も含まれるため安全に保管し、復元コピーで再承認する。削除は未実装で、期限での再利用停止と区別する。[詳細手順](phase-8.md)

## 第9段階の選抜・セミナー運用

「評価・選抜」は初期停止。同業務の候補・期間・母数・理由を確認し担当確定する。未着手なら変更可能で旧タスクを停止する。「セミナー管理」は代表限定。本人確認後に参加者専用アカウントを作り、本人の初回登録を確認して承認する。カードは全文を保存せず、HMAC鍵は安全な環境設定で管理し不用意に変更しない。

3日前の処理は初期停止で、明示有効化とCLI/画面tickが必要。生成した再案内は別途代表承認、モック実行も別操作。停止/回答変更/開催編集で無効になった未試行原稿は再準備→再承認を要する。試行済みを勝手に再送しない。ワーカー例外は自動停止して固定エラーを記録する。復元コピーは選抜/スケジューラーを停止し登録を再承認待ちに戻す。[詳細と本番前の残課題](phase-9.md)

## 第10段階の複数事業運用

代表で「複数事業」を開き、確認済み6事業を明示登録する。既存の事業/顧客/LINEを自動移行しない。未提示の料金・地域は設定し、事業担当者に必要な事業だけを許可する。事業IDの取り違えや、旧共通画面への私的成果物の登録を避け、事業画面で扱う。

会計は記録済み額/未計測/推定を区別し、USDのAPI費を円の差額へ自動算入しない。原稿承認と外部操作承認は別。実API経路はなく、手動実施記録は外部照合済みではない。緊急停止はこの事業別拡張の新規実行を止め、旧LINE等を無断変更しない。

バックアップは画像/個人情報を含む平文DBなのでアクセスを制限する。復元コピーは事業側を緊急停止し再承認を要する。個人情報の論理消去と、WAL/バックアップ/媒体からの完全消去は別で、後者は保存義務・運用設計を確認する。[手順と残課題](phase-10.md)

## 第11段階の候補・検証計画

「新規事業開発」で候補を複数登録し、未設定の希望値を推測で埋めない。資料は利用許諾/公式性/日付を自分で確認し、仮説と代表確認を区別する。誤った資料は撤回し、旧提案を再承認しない。既存事業へは代表が明示選択し、候補から自動的に顧客へ連絡しない。

試算は月次/円建ての入力仮定であり、実績へコピーしない。資料/仮定変更で旧提案・内部計画が失効する。提案の承認は外部実行の承認ではない。予算/時間/KPI/撤退条件を確認し、内部チェックと実市場の検証を区別する。実績の記録区分を確認し、未計測や部分計測から達成率を出さない。

復元コピーは従来の隔離に加えて計画停止・提案/改善の再承認待ち。明示的な再承認/停止解除まで再開しない。実業務DBへ新版を適用する前にバックアップし、DB移行の承認を確認する。[手順と未実施項目](phase-11.md)

## 第12段階：営業・顧客管理の運用

「営業・顧客」で事業を選び、同意目的/停止/担当/次回日を確認します。代表が税区分・税率・行別端数処理を確認するまで見積承認・送信・契約を進めません。佐久市内6,000円の税込/税別は未確認のままです。人物参照の関連付けは両事業の本人確認・目的別同意を確認し、誤りは解除します。旧顧客を自動統合しません。

操作承認後も送信は始まりません。模擬実行と、代表が観測済みの事実を申告する手動記録を区別し、未確認事実を登録しません。部分入金/全額返金/未入金取消は対応、部分返金は未対応です。結果不明時は照合待ちで自動再送を止めます。

旧DBは保全し、上記backup/restore手順で新規コピーを作ってから新コードで版12を確認してください。復元は見積・操作を再承認待ちにし、事業の緊急停止を保ちます。旧DBをDROP/初期化/上書きしません。実データ切替/削除は別の代表承認が必要です。詳細は [第12段階の移行・復旧](phase-12.md)。

## 第13段階：業務・営業支援

ローカル起動後「業務・営業支援」で事業を選択し、既存営業案件を関連付けます。必要な社員だけに目的・根拠参照・期限・優先度を割り当て、固定テンプレートを確認して代表が承認/却下。停止後は出力作成と承認を拒否し、再開は代表が明示します。案内済み/成約/入金へ進める前に第12段階の人間確認記録が必要です。

セミナーの登録・区分・回答・3日前準備は既存画面で管理します。業務画面の案内承認は送信待ちまでで実送信しません。停止/同意撤回/参加拒否/開催変更後の旧案内は使用できません。欠席は未回答から推測せず、代表が開催後の確認根拠を記録します。

版13適用も先にbackup/restoreの新規コピーで確認。復元ではタスク全停止・成果物再承認、原稿送信待ちを再承認待ちにし、自動再開しません。旧DB/コードは保全し、破壊的ダウングレードを行いません。詳しい操作・復旧・制限は [第13段階](phase-13.md)。

## 第14段階：セミナー運営・本人申込

代表は「セミナー運営」で事業と開催月を選び、日時/場所/費用/定員/対象区分を手動設定します。新規は合成mockが初期値。本人確認と区分の承認は既存セミナー管理を利用し、本人が「申込・参加希望」で回答・目的別同意/停止・関心を入力。全体の再案内停止も優先します。

案内は固定テンプレート→代表の修正/個別承認→API未接続の送信待ち。追加予定は初期停止、代表の有効化と手動の本日分準備だけで、Web起動時に常駐実行しません。模擬結果不明は照合待ちとして再送を止めます。実参加/欠席は終了後、面談完了は本人の希望と過去時刻の根拠を確認。実予約/契約/入金を推測しません。

実データ適用前にbackup/restoreで新規コピーを作り、版14の対象区分と旧行を確認。復元は新予定/タスク停止・再承認、元DBは保全。ロールバックは旧コードと移行前DBコピーで検証し、旧コードを新DBに向けて新対象制限を失わないようにします。詳細は [第14段階の運用・制限](phase-14.md)。

## 第15段階：事業拡張の基盤

「事業基盤」で新規追加すると自動ID・準備中・開始日未設定可・AI割当制限有効で登録します。役割と顧客/収支は既存事業IDのまま、無効化でデータを削除しません。割当APIで作者と独立レビュアーの両方を指定し、外部送信/承認/課金の権限を付与しないでください。完成版の割当画面は未実装です。

旧事業は自動移行しません。明示採用→必要な作者/レビュアーの割当→代表のポリシー切替を確認。既存未完了タスクの担当が不足すれば切替を拒否します。開始日/料金/実績を推測入力しません。既存フォームとの競合は事業版とプロフィール版の両方で確認します。

適用前にbackup/restoreの新規コピーで版15と旧行を確認。復元時は割当停止・既存緊急停止を維持し、代表確認後に必要な範囲だけ再設定。ロールバックは旧コードと移行前DBコピーで行い、新ポリシー付きDBを旧コードへ向けません。詳細は [第15段階の手順/API/制限](phase-15.md)。

## 第16段階：事業別経営集計

既存 `/businesses` / `/business` の期間指定を利用する。代表が会計採用基準と追加KPIの集計規則・期間目標を確認するまで、未確認事項は未計測/要再確認とする。全事業の異なる税基準を合算しない。実DB適用前はbackup/restoreの新規コピーで版16と旧行保持を確認し、復元後の割当・自動実行を勝手に再開しない。詳細とロールバックは [第16段階の手順](phase-16.md)。

## 第17段階：紹介情報と顧客導線

`/customer-journey` で事業を選択。代表が紹介情報と根拠を確認し、目的別同意と現行AI割当を既存画面で設定する。未確認・期限切れ条件を承認せず、本人希望と同意なしに営業送信しない。登録した面談候補は未確定で、承認だけでも実行しない。公式原文は取得不可のため確認待ち。版17は移行前バックアップと復元コピーで検証し、復元後は紹介の再承認と割当の確認が必要。[詳細・制限・復旧](phase-17.md)。

## 第18段階：AI業務・引き継ぎ

`/ai-workflow` で事業と既存営業案件を選ぶ。目的別同意・現行担当がない場合は確認待ち。引き継ぎは同一事業だけ、成果物がある場合は代表の内部承認後に行う。失敗は30秒待機・最大3試行で停止。重要操作案は承認しても実送信/設定変更を起動しない。適用前は版18を復元コピーで検証し、復元後の業務・承認・割当を自動再開しない。[操作/API/復旧](phase-18.md)。

## 第19段階：事業・担当変更の準備

`/business-readiness` は準備済み変更案の確認・代表承認・別適用を行う。新規事業・担当変更はAPI/サービスで準備し、完成入力画面は第20段階へ残す。staleは新しいキーで確認し直す。担当解除は履歴保持、旧互換の当該担当にも現行権限制限を適用する。停止で顧客・会計を消さず、再開で自動起動しない。移行前バックアップ/復元コピー検証と未適用承認の再確認は [第19段階手順](phase-19.md) を参照。
