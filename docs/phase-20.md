# 第20段階：事業管理・既存28人の担当割り当て画面

確認日：2026-10-27（日本時間）。基点 `origin/main` = `8e8d359`（第19段階 PR #21 のマージ）。代表の第20段階指示書と追加回答7項目を実装要求とする。第13.5段階の商品計画と既存ロードマップの順序は維持する。

## 実装範囲

- `/business-management`：既存事業一覧、「＋ 新規事業を追加」。旧 `/businesses` にも追加ボタンを配置。
- `/business-management?new=1`：事業名、概要、カテゴリー、提供サービス、対象顧客、既存アカウントからの責任者、状態、対象月と売上・利益目標。
- `/business-management?business=ID&month=YYYY-MM`：編集・停止・再開、月次実績と目標、顧客登録・面談・契約の記録件数、担当社員、設定承認履歴。既存の顧客・問い合わせ・営業・予約・収支・KPI・引き継ぎ画面への同一事業リンク。
- `/ai-management?business=ID`：既存28人を全員表示。役割、許可された事業の担当状況、当該事業の未完了タスク数。担当業務、対応範囲、限定権限の追加・変更、論理解除。別事業で同じ社員を選べば兼務できる。未選択の社員・他事業には変更しない。
- POST `/business-management-confirm`：入力と現在の認証権限、編集開始時のスナップショットを検証し、保存前確認を表示。既存第19段階の `br_requests` / `br_events` を利用する。
- 確認→代表による承認→別操作で適用。却下可能。承認者・日時・変更前後・適用者を保存。承認だけでは設定に反映しない。適用はDBトランザクションで実行し、再適用は同一結果。外部操作は呼び出さない。

## 追加仕様7項目

1. 目標は事業・対象月ごとの円整数。売上は非負、利益は赤字目標の負数も許可、上限は絶対値1兆円。対象月は西暦YYYY-MM。入力を勝手に生成しない。
2. 空欄はSQL NULL、0円とは別。対象月の空欄保存で当該月の目標を未設定に戻せる。他月は保持。目標を台帳・実績・第11段階の試算へ追加しない。
3. 責任者は既存 `representative` / `business_operator` から選ぶ。選択でACLを追加・変更しない。実際の参照可否は従来の事業別ACLが決める。
4. 責任者変更も代表権限、変更前後確認、明示承認、適用、操作履歴が必須。適用時にも候補アカウントの現行役割を再確認。
5. 社員は再生成しない。既存の複合キー（事業ID・社員ID）と担当制御を利用し、1人が複数事業を担当できる。
6. PCとiPhoneは共通の認証付きWeb画面・同じサーバーDBを参照する設計。編集競合は古いスナップショットを拒否。ライブ更新やオフライン同期は未実装、更新は再表示で取得する。
7. 既存コード・データ・28人の設定を維持。移行は空の追加テーブルのみ。事業の自動登録、改名、統合、権限付与、顧客コピー、実送信はしない。

## データ・権限・互換性

`020_business_management.sql` は `office_migrations` の版20として一度だけ実行する。`bm_profiles` に提供サービス、対象顧客、責任者を保存し、`bm_month_goals` に事業ID・対象月の一意キーとNULL許容の目標を保存する。既存の `portfolio_businesses.services` は従来の概要として保持し、提供サービスと混同しない。既存顧客・料金・地域・収支・同意の移行や自動転用は行わない。新しい提供サービス等は内部管理情報であり、従来の顧客向け原稿へ自動反映しない。

第19段階のcreate/updateには省略可能な `management` オブジェクトを追加した。省略時の既存要求と挙動は維持する。オブジェクト指定時は必須キーを厳密検証し、updateの状態・有効性・確認フラグとの矛盾を拒否。新規の運営中設定には代表による提供状況確認が必要。公式条件未確認の案内は別の確認待ちを維持する。

編集開始→確認保存、承認、適用の各時点で競合を検証する。プロフィール・月次目標もスナップショットに含む。未適用変更は新しい確認を作り直す。停止はデータ削除ではなく実行権限制限、再開も自動実行しない。

設定・担当変更は代表のみ。事業担当アカウントはACL内の閲覧のみで、他事業と全事業リストを取得できない。社員の権限は参照/内部作業/集計参照のみで、外部送信や他者への権限付与は不可。担当解除は履歴と未完了業務を保持し、当該社員の実行を拒否する。人間が第18段階の引き継ぎを確認する。旧互換運用の事業は変更対象の社員だけ厳密制御し、未指定社員を無断で切り替えない。

共通の認証、CSRF、同一Origin、Host制限、CSP（スクリプト不可）、HTMLエスケープ、SQLパラメーター、入力長制限、監査、料金上限を維持。顧客の個人情報を全事業一覧に追加しない。代表向け設定確認には必要な事業責任者のアカウント名のみ表示する。

## 操作方法

1. 既存の代表アカウントでログインし、「事業管理」を開く。
2. 「＋ 新規事業を追加」から必要事項を入力。「変更内容を確認」を押す。
3. 変更前後・影響を確認してチェックし、「承認」を押す。この時点では未適用。
4. 「承認済みの設定を適用」を押す。事業一覧と詳細に反映する。
5. 既存事業は詳細の状態を変更して同じ確認・承認・適用手順で編集・停止・再開。
6. 月を選び「対象月を表示」。当月目標を編集する。未設定は空欄のまま保存。
7. 「AI社員管理」で事業を選び、社員を開いて担当と限定権限を入力。同じ確認・承認・適用を行う。別事業でも同一社員を選択できる。
8. 担当解除は未完了タスク数を確認し、別途引き継ぎを判断してから確認・承認・適用。タスクを消したり自動で別人に渡したりしない。
9. 競合エラー時は元画面を再表示し、最新設定を確認して新しい変更を作る。適用履歴は画面下部から確認する。

## 起動とPC/iPhone

既存手順 `python3 -m violet_office.web serve --open-browser` を使用する。初回アカウント作成はREADMEの `web init` を参照。既存データがある場合は初期化しない。画面URLは既存サーバーの `/business-management` と `/ai-management`。

**現行サーバーはループバック専用。iPhoneからの実接続は未対応・未実施。** 390pxのChromiumは表示・操作検証であってiPhone実機検証ではない。PC/iPhoneで同じデータを実運用するには、代表承認のうえ、到達可能な同一サーバー、HTTPS、信頼済みHost/Origin、Cookieと認証の保護、適切なアクセス制限、バックアップ、実機検証が必要。現行のHost/Origin/ループバック制限を無効化する手順は提供しない。端末ごとにSQLiteをコピーして同期する構成にはしない。本番公開やネットワーク公開は今回未実施。

## 安全な移行・復旧

今回、本番DBは開いていない。Office起動時に追加移行を適用する既存方式なので、本番起動前に代表がバックアップと検証用コピーでの確認を行う。

- 既存 `violet_office.ops` のバックアップ手順と第6段階運用手順を使用する。
- 検証用コピーで移行を2回実行し、既存行保持・外部キー整合性を確認する。
- 復旧は既存のrestoreコマンドで**新しいパス**へ復元し、既存DBを上書きしない。セッション無効化・担当停止・未適用承認の再確認は従来どおり。
- 第19段階へアプリだけ戻す場合は追加2テーブルを残す。DROP/列削除は不要。第20段階追加項目を旧画面で編集できないことを明示し、新規作業を止めて確認する。適用済み変更の自動逆転はしない。
- 追加テーブルを含むバックアップ・復元テストを実施済み。実際の業務DB復旧は今回未実施。
