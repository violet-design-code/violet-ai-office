## D. 定期タスクの実行状況・仕様

スケジュールは初期作成時に停止。代表が有効化し、画面で「1回実行」するか、CLIのwatchを明示起動した場合だけ処理する。Web起動だけではスケジューラーを起動しない。watchや本番運用をこの作業で常駐させていない。

- 日次/週次/月次は各1件。JSTの初回日時・当期/前の完了期間・下書き準備の有無を代表が設定
- 停止後に設定を編集できる。設定版を上げ、同じ期間でも設定を意図的に変えた実行を区別する。古い設定の途中処理は継続できない
- 日次は翌日、週次は指定曜日、月次は元の指定日。31日指定は存在する末日に丸め、翌月に31日に戻す。月末が短い月でずれ続けない
- 停止中の全履歴を自動遡及せず、再開時点の最新期間だけ処理。レポート再計算は新しいキーを使用
- 1回のtickは最大3頻度。1レポートは最大6工程、提案タスク最大7件。実行はレポートごとに最大3試行
- 準備を含む経過10秒または期限切れを検出したら、次の工程へ進まない。単一のPython/SQL処理を強制中断するハードリアルタイム保証はない
- 同じスケジュール/設定版/期間は一意。排他リースとトランザクションで重複実行を防ぐ。成功した中間成果物をハッシュ検証して再利用
- 失敗時はスケジュールを自動停止。生の例外・API応答・秘密を保存せず固定コードを記録。代表の再開後のみ再試行し、3回を超えたら停止
- 手動停止/設定変更を障害と区別。強制終了後の期限切れリースは隔離し、勝手に再実行しない

試験用一時DBでは日次・週次・月次の3レポートと14工程を実行し、すべて代表承認待ち、実行後のスケジュールは停止した。実ユーザーのスケジュール・目標は作成していない。

## E. KPI・予算・時間の分析

日別の1指標・区分ごとに正規の集計値は1つ。2つの情報源を重複加算せず、訂正は最新IDを明示して新版を追記する。元データは残す。未来日の手動実測は拒否し、推定/モックとして区別する。

期間の全日分の手動実測申告が揃わない場合、記録済み合計を部分計測とし、月間達成率を出さない。欠損日を0と仮定しない。明示の0は計測済み0。推定、モック、実測申告は混ぜない。

顧客コホート/流入経路が未接続なので本当の転換率・因果関係・施策別の成功評価は未計測/未評価。必要な同期間データが揃った場合だけ、参考の「期間件数比」を別表示する。0分母では計算しない。目標0の達成率も割算しない。週次/日次を月間目標へ直接減算せず、別途月初からの計測範囲を使用する。

料金は既存office_costsの手動確定/推定を別集計。モックを除外。実APIの自動請求照会はない。明示したAI予算は月間上限にも反映し、従来の全体上限を勝手に上げない。ローカル処理の予約額は0で、有料API呼出経路自体がない。予算0を本番利用許可と扱わない。

代表時間は自己申告の記録済み分のみで、未記録分は不明。明示上限0または記録済み時間が上限に達した場合は任意のSNS下書き作成を抑止し、負担整理を提案する。再試行時は最新の稼働上限も確認する。集計用に凍結した目標を勝手に最新値に書き換えない。

## F. レポートと日本語指示

日報は完了/作業中/承認待ち/エラー、計測実績、次期優先業務。週報は期間集計、月目標との関係、未評価の施策、翌週提案。月報はKPI、契約/面談、費用、次月提案を保存する。人のレビュー完了タスクと機械的処理完了を分ける。参照ID一覧は最大1000件で、総数は別計測。

対応する6例:

| 指示 | 処理 |
| --- | --- |
| 今日の仕事を報告して | 日次の実績・ローカル作業・優先案 |
| 来週の集客計画を作って | 今週までのデータを根拠に翌週の計画案。次期数値目標を自動確定しない |
| 紹介者が紹介しやすい文章を考えて | AI16の固定テンプレート案、AI28の機械検査、原稿承認待ち |
| 面談予約を増やす改善案を出して | AI18の仮説と同意を尊重する導線、検証案。効果保証なし |
| 今月の目標達成状況を教えて | 月目標・計測範囲・差・達成率の可否 |
| 今月のAI利用料金を教えて | 月間の手動記帳の確定/推定、未計測の区別 |

ルール判定であり自由な日本語理解ではない。未対応の指示はエラー/要確認として旧来の担当割当画面で扱う。

レポートは入力/目標版/実績のスナップショットを固定して保存。入力訂正後の再分析は新規レポート。担当・タスク・成果物・ハッシュ・期限・承認状態を確認可能。改変した中間成果物やレポートは再利用/承認できない。

計画承認は割当済みの提案タスクをローカル手動作業として開始可能にするだけ。SNS原稿、LINE、連絡、予約の実行を承認したことにはならない。原稿の現行10項目チェックと別の代表承認を省略しない。計画の修正依頼/却下/承認と操作履歴を残す。

## J. 代表が次に行う操作・起動

Python 3.12以上、追加ランタイム依存なし。初回だけ:

```sh
python3 -m violet_office.web init
python3 -m violet_office.web serve --open-browser
```

Windowsはpython3を `py -3` に置き換える。既存ユーザーがある場合initは再実行不要。PC内ブラウザのアドレス欄は `http://127.0.0.1:8765/` 。代表でログインし「目標・定期業務」を開く。

1. 代表の目標・予算・稼働上限を必要な項目だけ入力。未設定は空欄のまま保存。
2. 匿名の日別実測申告/推定を根拠とともに入力。訂正は最新IDを指定。個人情報やキーは書かない。
3. 「今日の仕事を報告して」などを実行し、未計測/仮説/提案・担当と期限を確認。
4. 日週月スケジュールを停止状態で作成し、日時と対象期間を確認してからローカル有効化。
5. まず画面の1回実行で確認。レポート・計画は承認待ちで停止し、原稿も別途承認する。
6. 継続する場合だけ下記watchを明示起動。終了はCtrl+C。すべて止めたい場合は画面でも各スケジュールを停止。

```sh
python3 -m violet_office.growth_cli status
python3 -m violet_office.growth_cli tick
python3 -m violet_office.growth_cli watch --interval 30
```

単発レポートは `python3 -m violet_office.growth_cli run --cadence daily --key YOUR_UNIQUE_KEY` 。週次/月次はweekly/monthly、直前期間は `--period previous` 。既存ファイルの--db指定も可能だが、実顧客データや本番キーをテストに使わない。

ワーカーを止めても有効化設定は保持される。Web起動だけでは自動再開しない。設定変更は停止してから行い、新設定版の実行として記録する。復元コピーでは全スケジュールを停止し、実行中レポートを隔離、承認済み計画/提案も再承認待ちにする。元DBは変更しない。

外部送信、本番公開、課金を伴う新規利用、既存データ削除、本番運用の開始は行っていない。
