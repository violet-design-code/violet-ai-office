## 1. 現行と候補スキーマ

|テーブル|現行925db46|初回導入の検証候補|
|---|---|---|
|acct_task_policies|task_id TEXT NOT NULL → tasks.id、policy_id TEXT NOT NULL → acct_policies.id、approved_by TEXT NOT NULL → office_users.username、複合PK(task_id,policy_id)|列順・型・PK・既存FKを維持。policy_id、approved_byの索引を追加|

SQLiteの通常のrowidテーブルではTEXT PRIMARY KEYだけでNOT NULLを保証しないため、候補は明示します。現在のアプリは実タスクIDを渡しますが、DB制約としても欠損を拒否する案です。

追加索引候補は `acct_task_policies_policy_idx`、`acct_task_policies_approver_idx`、`acct_task_reads_business_idx`、`acct_task_reads_policy_idx` の4件です。複合PKの先頭task_idでタスク別承認参照を処理でき、task_id単独索引の重複追加は不要です。FK子列のpolicy/approver/businessは親レコードの検査にも使います。索引は権限付与ではありません。

既存のアプリの3列のINSERT順序を維持する候補です。承認情報・分類マーカーを移行時に自動投入しません。

### DB制約とアプリ認可の境界

個別FKは存在するタスク・事業・ポリシーを保証しても、それらの事業/社員が一致することは保証しません。合成DBで、個別参照は有効な他事業の組み合わせを直接SQLで作れても、bind_taskとLegacyAccountingが拒否することを確認しました。DBへの直接書き込みをAIへ許しません。

DBだけでも組み合わせを拘束する将来案には、task_policiesへのbusiness_id追加、親の適切な複合UNIQUE、(business_id,task_id)/(business_id,policy_id)の複合FK等が必要です。現在の位置指定INSERTも修正が必要なため、今回の互換候補へ無断で追加しません。

readsのPKはタスクごとの分類マーカーの重複を防ぎます。複数回の取得履歴を保存する表ではなく、INSERT OR IGNOREにより最初のpolicy_idを保持します。失効後に別の正当なポリシーで取得しても、分類マーカーは旧IDのままであることをテストしました。現在の承認は必ず動的認可で確認します。

policiesの複合PKは同じタスク/ポリシーの二重登録を防ぎますが、同タスクへの複数ポリシーは可能です。旧経路は有効候補が複数なら曖昧として拒否します。勝手に広い方/新しい方を選びません。

### 監査メタデータを増やす場合

現行のtask_policiesは関連付け時刻・ポリシー版を列として保持せず、acct_eventsのtask_boundにもタスクIDがありません。したがって既存3列だけでタスクごとの完全な承認履歴を復元できるとは扱いません。readsにも取得日時や2回目以降の全取得はありません。

本番前に、関連付けのbound_at/ポリシー指紋/承認目的の版を追加するか、別の専用監査記録にtask IDと固定アクションを残すかを代表が決める必要があります。列を追加する場合は、現行の位置指定INSERTを明示列付きINSERTへ変更するコード対応を先に検証します。今回の互換候補は3列のままの原子性検証であり、完全な監査履歴スキーマの完成を意味しません。監査・報告UIの正式仕様と合わせて確定してください。
