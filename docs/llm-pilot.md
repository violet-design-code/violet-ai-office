# 生成AI連携・第1弾：Instagram下書き試験

確認日：2026-10-28（日本時間）。作業ブランチ `feature-llm-instagram-pilot`、基点 `b9bb4e7`（第20段階とスケジュール追加を含む）。代表の生成AI連携・第1弾指示を要求とし、他段階・経理自動化へは進まない。

## 今回できること

事業別・本人認証付きの `/llm-pilot` 画面で、Instagram投稿の依頼を受け、次の4工程を保存・引き継ぐ。

| 工程 | 既存担当 | 内容 |
|---|---|---|
| 1 | AI01 統括本部長 | 依頼を整理し、AI07・AI09への割当案を作る |
| 2 | AI07 マーケティング部長 | 対象・テーマ・CTA・未確認事項を企画 |
| 3 | AI09 投稿文章作成担当 | 1〜3件のタイトル・本文・ハッシュタグ・CTAを作成 |
| 4 | AI01 統括本部長 | 保存済み成果物を参照し、問題点・代表向け報告を作る |

28人の役職・設定・enabled・外部権限は変更しない。担当を自動追加しない。モデルを使う担当はこの3人だけで、AI01は2工程。実モデル未接続時は明示した合成モックで動作する。AI01の最終確認も生成モデルによる提案であり、正確性や法令適合を保証しない。最終的な事実・権利・個人情報・表現の確認と承認は人間が行う。

今回の実検証はモックとHTTPトランスポートの差し替えのみ。OpenAIへの実リクエスト、課金、Instagram投稿、LINE送信、外部公開は0件。実API接続・実モデル品質は未検証。生成AIをすでに本番稼働させたという意味ではない。

## 既存機能との統合

- 元の「統括へ指示」のキーワード方式は維持し、専用入口から事業IDと現在の担当権限を検証する。
- AI01/AI07/AI09それぞれに対象事業の有効な `business_read` と `work` が必要。事業停止・全事業緊急停止・役割変更・割当解除があれば拒否/保留する。旧互換モードの暗黙許可は使わない。
- 顧客情報や他事業のデータを自動でモデル入力へ取り込まない。入力は代表が確認した匿名・公開可能な素材と同一依頼の前工程成果物のみ。
- 4工程は `lp_steps`、呼出しは `lp_calls` へ保存。従来の成果物管理にはAI01集約タスクと本文を含まない参照成果物を追加し、既存 `reviews` / `approvals` を通じて代表判断を記録する。
- 既存の一般画面から、この集約タスクの開始・レビュー・承認を迂回できない。事業別の専用画面で人間が確認した場合だけ既存承認へ接続する。
- 人間による確認は既存指定レビュー担当の確認項目を代表が手動記録したもので、AI28をモデルで稼働させた記録ではない。
- 下書き承認後は `approved_draft_no_execution`。投稿・送信・公開を行う関数は追加していない。モデル利用許可と、原稿承認、将来の公開許可は別。
- モデル出力は実行命令として解釈しない。担当候補をAI07/AI09に限定し、JSONキー/長さ/件数を検証。シェル・ツール・URL取得はモデルに与えない。秘密情報やメール・電話等を含む入力/出力は保守的に拒否する。完全な個人情報検出を保証するものではないため、入力前の本人確認が必要。
- 工程別の詳細実績は新しい試験画面で確認する。既存の社員評価へAI07/AI09のモデル工程を自動合算する機能は未実装。

## 代表が最初に行う操作（課金しない）

1. **現在のWindows側の正しい業務DBを先に特定する。** 事業一覧が空の問題を新規登録で埋めない。練習用DBと既存DBを取り違えない。今回はWindows側のDBには接続していない。
2. 正しいコード・DBのバックアップを確認する。既存手順の `python -m violet_office.ops backup --db 実際のDBパス --output 新しいバックアップパス` を使用する。出力先は必ず未使用のものにする。パスに空白があれば引用符で囲む。
3. 本ブランチを別途確認して利用する。未コミット変更を破棄せず、既存の第1〜20段階とスケジュールを保持する。
4. 環境の `VIOLET_LLM_LIVE_ENABLED` を0のままにする。モックではAPIキー・モデル・価格・有料予算は不要。
5. `python -m violet_office.web serve --db 実際のDBパス --open-browser` で起動し、代表アカウントでログインする。initは既存DBに実行しない。
6. メニュー「生成AI下書き試験」または `http://127.0.0.1:8765/llm-pilot` を開き、既存事業を選ぶ。
7. AI01/AI07/AI09の既存担当・参照/内部作業権限を確認する。不足時は実行を拒否する。必要な変更は代表が既存の担当画面で確認→承認→適用し、この機能による自動付与はしない。
8. 「Instagram投稿の下書きを作成してください。未確認の料金・条件は断定しないでください」など、匿名の依頼を入力。1〜3件、実行区分「モック」、確認チェックを選び登録する。
9. 依頼内の実行確認をチェックし「4工程をモック実行」。AI01→AI07→AI09→AI01の出力・未確認事項・ログを確認する。
10. 最後は「代表承認待ち」で停止する。人間の確認記録とチェックを入力して下書き承認/却下を選べるが、承認だけで公開・送信しない。
11. 「全体停止」または依頼の「停止」で新しい実行を防止できる。停止解除・再開操作だけで実行は始まらない。

APIキーを登録しなくても、モックの一連の操作を検証できる。事業が登録されていなければ処理を止め、既存データ調査を完了してから進める。アプリが初期事業や担当を勝手に作ることはない。

## 実API接続に必要な設定（今回は接続しない）

OpenAI Chat Completions向けの実HTTP送信コードを用意した。固定宛先 `https://api.openai.com/v1/chat/completions`、TLS検証と既存プロキシを維持し、リダイレクトを拒否する。任意の接続先を入力できない。

| 設定 | 用途 |
|---|---|
| `OPENAI_API_KEY` | プロセス環境からのみ取得。ソース・DB・ログ・チャットへ保存しない |
| `VIOLET_LLM_MODEL` | 利用権限があり、JSON形式出力とmax_completion_tokensに対応するモデル名 |
| `VIOLET_LLM_INPUT_USD_PER_MILLION` | 正式価格を確認した入力USD/100万token。未設定なら停止 |
| `VIOLET_LLM_OUTPUT_USD_PER_MILLION` | 正式価格を確認した出力USD/100万token。未設定なら停止 |
| `VIOLET_LLM_PRICE_REFERENCE` | 公開可能な価格出典・確認日等。秘密情報を記入しない |
| `VIOLET_LLM_TIMEOUT_SECONDS` | 1〜30秒、既定20秒。通信待ち時間と応答読み取りの期限を制限 |
| `VIOLET_LLM_MAX_OUTPUT_TOKENS` | 128〜3000、既定1500 |
| `VIOLET_LLM_LIVE_ENABLED` | 既定0。今回は0を維持する |

`INTEGRATION_MODE=mock` は従来のLINE・予約等の連携設定で、生成モデルの依頼モード・有料許可とは別に維持する。

`.env.example` は項目の見本であり、`.env` をアプリが自動読込することはない。OSの秘密情報管理等から、起動プロセスだけへ渡す。キーをコマンド履歴へ直接入力する手順や、ブラウザーの入力欄へ保存する機能は設けていない。

将来の有料接続には、利用するOpenAIアカウント・モデルの可用性、価格と条件、匿名化/外部提供の確認が必要。全体月次予算（AI経費）と事業月次予算（既存事業管理）を設定し、代表が依頼ごとに「有料API利用を許可」を明示したうえで、さらに実行操作を行う。環境フラグだけでは起動しない。価格/モデル/キーの変更は許可を無効にする。

今回は外部接続を禁止する指示のため、これらの有料許可・フラグ有効化・実API実行は行っていない。実モデルの対応可否や最新価格の実査も未実施であり、将来の接続前にOpenAI公式API/価格資料を確認する。

## 費用・時間・失敗処理

- API呼出し前に、入力サイズと出力上限、設定価格から保守的なmicroUSD予約額を算出。全体と事業の既存月次予算、既存費用と予約、他の試験呼出しの予約をトランザクション内で照合する。未設定・0予算なら有料実行しない。
- ネットワークIOは書き込みトランザクションの外。実行権の確保と予約、結果・費用の保存は別の短いトランザクション。
- 実行区分、モデル、工程・担当、試行回数、要求ハッシュ、開始/終了、固定エラーコード、入力/出力トークン、価格出典、推定費用を保存。APIキー、原文のHTTPエラー、ヘッダーは保存しない。依頼本文と成果物は認証付きの事業別保存で、アクセスログには出さない。
- モックのトークン数は合成値・費用0。実応答由来の使用量と区別する。モデル応答由来の金額も**推定**であり、確定請求ではない。割引・税・為替・価格改定・課金システムの詳細は自動照合しない。OpenAIアカウント側の上限設定も別途必要。
- 推定費用は既存 `office_costs` へ記録し、モデル/日/月/部門/集約タスクの集計と事業別経費表示に接続する。モックを実費へ合算しない。予算計上月/費用日は呼出し開始時の日本時間に揃える。
- 正常成功の再実行を防止。画面の工程番号も照合し、古い実行フォームで次工程が勝手に進まない。
- 明確な429拒否だけ、30秒後に手動再試行可能、工程ごと最大3回。自動の無限再試行はない。
- タイムアウト、ネットワーク結果不明、5xx等では予算を保持して `reconciliation_required`。重複課金防止のため自動再実行しない。90秒以上応答がない途中呼出しは、代表が照合待ちへ隔離できる。
- 実APIの課金/結果の照合と、不明予約額の解除を行う操作は未実装。結果不明時にSQLで勝手に予約額を消したり、新しい依頼で同じ処理を繰り返したりしない。
- モデル呼出し中の停止は、提供元で開始済みの処理や課金を取り消す保証ではない。結果を保留し、後続工程を止める。保留結果や変更後の権限は人間が確認する。
- JSON不正、許可外担当、秘密情報等は原稿へ昇格させず失敗とし、判明した使用量・推定費用だけ記録する。

クラウド内に存在した `office.sqlite3` / `phase3-sample.sqlite3` / `phase4-mock.sqlite3` を、変更前に `var/backups/*-before-llm-*.sqlite3` と検証マニフェストへ保存した。これらは過去の開発用DBであり、Windows側の事業登録DBのバックアップを取ったという意味ではない。

Web CLIは既存DBの初回利用時、Store/Officeによる起動時書き込みより前に整合したSQLiteバックアップを新規パスへ保存する。追加移行22自体も、その直前のスナップショットを新規パスへ保存する。起動前/移行前の2時点を取る場合がある。バックアップ失敗時は安全に停止し、この移行を実行しない。既存ファイルを上書きしない。保存先は既存DBの親フォルダー配下 `backups`。

`022_llm_pilot.sql` はジョブ・4工程・モデル呼出し/費用・停止制御・監査の5テーブルを追加する。既存テーブルの削除・再初期化・事業/担当の再生成はしない。再起動では移行済みを検知し重複作成しない。

バックアップは平文で、業務データ/個人情報を含む。従来どおりアクセス制限付き保管と既存opsの復旧手順を使用する。復元は新しいパスのみ。未完了ジョブを停止、実API許可を解除、途中呼出しを結果不明へ保留する。旧版へ戻す際も追加テーブルを削除せず、試験を停止してからコードを戻す。業務DBの無断移行・破壊的ロールバックは行わない。
