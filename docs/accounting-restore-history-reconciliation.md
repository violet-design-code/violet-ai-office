# 復旧前後の承認・失効履歴の照合手順

2026-10-29。読み取り照合の設計と合成試験の記録です。本番用CLI/復元/書換え機能はありません。

## 1. 照合する三つの証拠

- **A 復旧直前の現在状態**：正式backupまたは保全したDB/WAL、承認・失効・監査、schema/全行manifest。破損で読めなければ未確認とする。
- **B 復旧候補の過去状態**：選定backupの検証済みmanifest、承認/関連付け/取得マーカー/handle/監査。
- **C DBとは独立した現在の信頼状態**：最新性を認証できるhead、系統/epoch、欠番のないsequence、承認/失効の内容digest/actor/task/scopeと結果。Bの中のコピーをCとして使わない。

A/B/Cの採取時刻と系統を一致確認する。Cが欠ける/古い/到達不能/署名不正なら会計停止継続。Aが読めなくてもCで失効だけ分かれば完全復旧できるとは扱わず、データ喪失の評価も続ける。

## 2. 照合の順序

1. 取得前に独立ゲートをclosedにし、代表と復旧担当が証拠採取権限・保管先を確認する。
2. Cの最新headを独立認証し、連番・前digest・署名/鍵版・系統・時刻・重複決定ID・内容digestを検証。単にファイルがあるだけでは信頼しない。
3. A/Bのschema版と列順/型を先に検証し、ID/状態/承認者/expiry/fields/business/agent/目的/期間の正規化形式を定義。未知schemaや解釈不能な日付/JSONは停止。
4. 各policyのproposed→approved/rejectedまたはpending/approved→revokedの成功イベントを順に照合。拒否イベントは状態遷移と区別する。成功監査とstatus、承認者/時刻/内容が一致しない場合停止。DBから消えたpolicyや監査も差分扱い。
5. Bの履歴がCに存在することを確認。Cにだけある後日のrevoked/rejected/expired/承認/内容変更/取得・受領は「復元で失われる後続履歴」として保全する。旧approvedを現在許可へ昇格させない。別系統のイベントを混ぜない。
6. AとCの不一致、未完了intent、task/内容版証拠欠損、既存監査に無いイベントを一覧化。履歴不足は都合よく補完しない。現在のacct_eventsだけではtask関連付けの完全証拠がないことを明記する。
7. 全テーブルのA→B差分から、監査以外の失われる情報も一覧化。Cへ会計値や全文を転記せず、参照ID/固定分類/digestで証拠を保護。
8. 代表が照合結果とデータ喪失を確認しても、旧policyは隔離のまま。整合性修復承認後、新epochで新policyを個別申請・承認する。例外による履歴未確認の解除は本手順に含めない。
9. 取得時に毎回、新epoch/receipt/最新独立許可＋DB側認可を再確認。再取消後に古い再承認要求・receiptを再送しても通さない。

## 3. 判定例

|B（バックアップ）|C（最新証拠）|判定|
|---|---|---|
|approved|後日revokedを確認|旧承認は拒否、失効履歴保全。古いIDは再承認しない|
|revoked|同じrevokedを確認|拒否を維持|
|approved|欠落/最新か不明|照合不能、停止継続|
|approved|監査statusが矛盾|停止し調査|
|pending/期限切れ|承認済みと説明されるが証拠不足|拒否、推測で許可しない|
|旧approved|完全照合後に代表が新policy承認|新scopeだけ、旧ID/handleは無効|
|他事業policy/AI04|代表名の新receiptがあってもrole/事業違反|拒否|
