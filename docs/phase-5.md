## 起動条件

- Python 3.12以上、Git。実行時の追加Pythonパッケージは不要
- 管理するPC上にこのリポジトリを配置
- 初期状態は空のローカルDB。サンプル実績やユーザーを自動投入しない
- 秘密値の入った.envは不要。初回に代表と閲覧者のパスワードを対話入力する

Mac/Linux:

```sh
cd /path/to/violet-ai-office
python3 -m violet_office.web init
python3 -m violet_office.web serve --open-browser
```

Windows（PowerShell/コマンドプロンプト）:

```powershell
cd C:\path\to\violet-ai-office
py -3 -m violet_office.web init
py -3 -m violet_office.web serve --open-browser
```

代表ユーザー名はrepresentative、閲覧者はviewer。パスワードは各12文字以上で別々のものを設定する。確認入力も求め、入力は画面やログに出力しない。初期パスワード・固定の共通パスワードは用意しない。既存アカウントがある場合initは上書きを拒否する。パスワード再設定画面は未実装なので、DBを消して対処せず別途管理者の復旧手順を作成する。

ブラウザのアドレス欄に `http://127.0.0.1:8765/` と入力して開く。--open-browserはそのPCのブラウザを開くためのオプション。クラウド実行環境のサーバーを自分のPCのlocalhostとして開くことはできないので、ローカルPCにコードを配置して起動する。公開用URLやクラウドのプレビューリンクは作らない。

ポート変更は `--port 8766` のように指定する。常に127.0.0.1にだけbindし、外部公開用のbindオプションはない。停止は起動したターミナルでCtrl+C。再起動後もvar/office.sqlite3にタスク・履歴・設定・認証情報（ハッシュ）が残る。DBをGit管理しない。

## デスクトップから開く方法

初回init後、Windowsはscripts/start_office.batのショートカットをデスクトップに作成する。ダブルクリックするとローカルサーバーとブラウザを開く。Mac/Linuxはscripts/start_office.shをターミナルから実行、またはOSのランチャー/ショートカットに登録する。サーバー起動中はターミナルを閉じない。Windows/macOSの実機でのショートカット操作は未検証で、LinuxのChromiumとHTTP入口で動作確認した。

## 実行できる範囲

自然文の自由な意味理解・任意の原稿生成は未接続。依頼文をキーワードで分類し、役割設定を参照して複数担当へ割り当てる。指定の4つの例はそれぞれ企画/紹介/分析/戦略の担当を選ぶが、紹介文5種類や自由な集客戦略をAIが生成するわけではない。未知の依頼は要確認。テンプレート生成は別の明示的な画面で媒体・7/14/30日・開始日を指定する。

社員画面の「開始」は手動作業をclaimする操作でありLLM起動ではない。「一時停止」はローカル状態を止め、手動作業の実行履歴をcancelledとする。外部プロセスの強制終了はしない。失敗タスクの再依頼は新しいタスクIDにし、旧履歴を残し、未着手の依存関係を差し替える。収集済みの依存成果物やキャンペーンの部分再実行は拒否する。既に進んだ成果物や承認を使い回さない。

担当作業は開始後、匿名化した成果物を手動登録できる。指定レビュアーの確認事実を代表が記録する方式で、自動レビュー合格と偽らない。レビュー後の代表承認も別操作。優先順位は依頼単位で変更する。原稿修正は新しい版として保存し、監査・確認・承認をやり直す。

原稿承認には第3段階の全確認記録が必要。修正依頼・却下は送信せず履歴に残す。外部操作の台帳は第4段階のモックだけを対象にし、現行承認ゲートを再利用する。承認後もdispatchするWebルートは存在しない。予約承認はモック枠の保留までであり、実予約確定ではない。外部操作への修正依頼後の再提案画面は未実装。

## KPIと費用の定義

- 本番の問い合わせ、紹介、予約、契約、SNS投稿、LINE登録、SNS流入はすべて未計測。モックDBにデータがあっても本番実績に混ぜない
- 本日のタスクはcreatedイベントを日本時間の日付で集計。ローカルタスク状態は既存DBから計測。タスクが一切なければ本日/完了は未計測。承認待ち0は各台帳を調べたローカル件数
- 社員の最終実行はclaimedイベントから取得。作成しただけで実行済みとは表示しない
- API請求の自動取得は未接続。実利用の手動記帳・モック、推定・確定を別々の区分で集計。請求や費用を自動生成しない
- 新しい会計台帳はUSDの整数micro USD。料金登録は記帳であり課金ではない
- 月間上限は日本時間の年月、既定0。有料作業の費用予約は月間上限と従来Storeの全体上限の両方で拒否できる。無料の手動作業は継続可能。既存DBの従来上限を勝手に引き上げない
- 月間判定は手動推定・確定の記帳額と新しい予約額を保守的に加算する。予約精算や推定から確定への振替は未実装で、同じ費用を複数回登録すると残額は小さくなる。既存予約は別枠表示。ライブ課金実行器は存在しない

## セキュリティ

パスワードはsalt付きscrypt。CookieのセッショントークンはDBにSHA256ハッシュのみ保存。ログイン時にセッションを変更、ログアウトで失効。最大8時間・無操作30分。匿名ログインフォームにもCSRFを発行する。ログイン試行は全ローカル利用者を通じて10分10回に制限するため、失敗が多い場合は時間をおく。

すべての変更はPOST・CSRF・Origin照合・代表ロール検査を通す。Host検証でDNS rebindingを抑止。SameSite=Strict/HttpOnly Cookie、CSP、frame拒否、nosniff、キャッシュ抑止、same-originリファラポリシーを適用。ブラウザPOSTのOriginがnullになる組合せを実ブラウザで発見し、同一サイトの送信元を維持するポリシーに修正した。null Originを許可する緩和はしていない。

同じコマンドnonceの再送は同じ結果を返す。一致しない入力のnonce流用は拒否。操作監査に認証済みユーザー名・固定操作名・参照ID・日時を保存する。業務の元データ・履歴と紐付き、承認だけで実行しない。アクセスログにURL・本文・Cookie・パスワードを出さず、エラーは固定文言とコードを表示する。

本文はHTMLエスケープ。一般的なメール・電話・LINE ID・一部の秘密値パターンは表示時に伏せる。成果物本文は代表だけが閲覧可能。自動匿名化・秘密検出は完全ではないため、本番の個人情報や秘密値を入力しない。実顧客データ投入前に専用の入力/閲覧ポリシーが必要。

HTTPはPC内の開発運用限定。Secure Cookie・TLS・MFA・OS外のアクセス防御・監査の改ざん耐性・本番鍵管理・バックアップ復元・保存期限削除は第6段階の課題。PC利用者・ファイルアクセスは信頼境界であり、既存CLIはOS権限で管理する。インターネットやLANへ公開しない。
