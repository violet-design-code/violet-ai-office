# D方式：外部信頼基盤の導入仕様案

2026-10-29（日本時間）。基点 `25a76039b493148615eb77a053d08749725d3875`。
本書は設計案。外部サービスへの接続/照会/契約、認証基盤の登録、課金資源作成は行っていない。製品仕様・料金・国内リージョン・利用条件の最新確認は、別承認後の選定工程で行う。従来の資料に記録した公式参照情報と既存コードを基に整理する。

関連：[Windows分離](accounting-windows-isolation-spec.md)、[中断証明](accounting-verified-abort-spec.md)、[検証・承認](accounting-preconnection-validation-plan.md)。

## 1. 推奨する構成

D方式のローカル台帳は維持する。その外側に、次の役割を分離する。

- **A 管理API/状態DB**：登録、policy/epoch、停止、出力予約、更新sequence、未完了操作を取引可能な保存先へ記録する。許可はこのAPI経由だけで発行する。
- **W 独立した最新確認先（witness）**：Aの現在head、系統・世代、連番、停止/予約状態のdigestを追記・単調更新する。Aの通常運用者にWの削除/復元/再初期化権限を与えない。
- **監査保管**：順序付きイベント/確定receiptを改変保護・別権限で保管する。WORM等は履歴保持の補助であり、現在headの確認や順序制御を代替しない。
- **代表本人確認/鍵管理**：代表の再認証と操作内容の結び付け、サービス認証、署名鍵と検証鍵の分離を担当する。PC側は外部の署名秘密鍵を持たない。

ローカル/A/Wのheadと未完了状態を照合し、どれか不明なら会計を拒否する。PCのcacheや最後の正常状態だけで許可しない。Windows側の照合サービスは会計値を送信しない。

AとWを同じrestore jobや同じ強い管理資格で一括変更できるなら、独立性はない。同一cloudでも管理権限・復旧権限・保管の分離が必要。異なるproviderでも同じ鍵/資格の侵害で両方を操作できるなら不十分である。

## 2. 実際に導入する際の候補比較

|候補|構成例（未選定）|利点|確認すべき制約・運用|
|---|---|---|---|
|Azure中心|Functionsまたは管理されたAPI、transaction対応DB、別管理のwitness API、immutable監査保管、Entra等の本人確認、鍵管理サービス|Windowsの組織/機器認証と揃えやすい候補。管理サービスでOS保守を減らせる|DB/APIの固定費、本人確認の契約条件、独立管理者/復元権限、WORM保持、条件付き更新と強整合を実構成で確認|
|AWS中心|Lambda等のAPI、条件付き更新/取引を使うDynamoDB等、別accountのwitness APIとObject Lock等の監査保管、ID/KMS基盤|状態更新と監査保管を分ける候補。小容量のメタデータ処理に適する構成を検討できる|認可判断に使うreadは強整合が必要。遅延複製/索引/cacheを現在headにしない。別accountの管理権限・復旧/保管条件を検証|

現Windows環境向けの**第一候補はAzure中心の構成**とする。ただし採用決定ではない。既存のID契約/運用者が利用できない場合や固定費が予算に合わない場合はAWS等と同じ要件で比較する。Wの実装と管理者分離が成立しなければ、いずれも導入しない。

既製のobject storageへ署名済みファイルを置くだけでは不十分。最新headを単調に扱う認可されたAPI、分岐/欠番の検出、登録系統、障害時停止を作る必要がある。cloudの管理者が持つ能力や現在のSLAを未確認のまま保証しない。

## 3. 状態・更新APIの契約

識別子はorg/instance、authority generation、recovery epoch、businessの不透明参照、policy ID/版、task/agent参照、scope digest、operation ID、delivery ID。headは(epoch, sequence, digest)と登録系統に結び付ける。時間だけを新旧の根拠にしない。

- 新しい更新はexpected head/版と一意operation ID、前イベントdigestを要求する。比較更新/CASと監査追記を同一取引にする。競合は再認可して再試行し、古い承認を無条件上書きしない。
- AとWをまたぐ操作は単一transactionとは称さない。Aでpendingを永続化→Wが現在headとの連続性を検証してack→Aで確定→ローカルと確定receiptを照合。途中失敗/commit不明は許可しない。
- 取消/停止intentは新規許可を先に禁止する。中断証明/全出力終了を確認するまではcompleteにしない。W更新失敗も未完了で保持する。
- 現在値取得は新規nonceに対する認証済み応答とし、instance/authority generation/epoch/head/状態を束縛する。署名鍵ID・信頼root・key rotation・失効を検査する。古い署名や期限内cacheへfallbackしない。
- 出力予約/終了/中断証明もheadの保護対象。policy更新だけをwitnessへ記録して、予約履歴の巻き戻しを見落とさない。
- 同一operation ID＋同一内容の再試行は同じreceiptを返し、監査や解除を二重に行わない。異内容なら拒否する。idempotency記録をTTLで消して古い承認を再実行可能にしない。

初回登録は独立した代表確認・単回enrollment proof・未使用の組織/系統登録に結び付け、CLOSEDで開始する。空ファイル/新しいランダムinstance IDを作るだけの再登録は禁止。外部側の系統/authority generationも復元で自動リセットしない。

## 4. 管理者による巻き戻しと復旧

Aの管理者が古い正規snapshotを復元して新nonceに答えても、Wの最新headとの不一致で拒否する。通常運用者はWの管理資格を持たず、Wの変更には別の管理主体と監査付き承認を要する。

Aの復旧時は先に全体停止し、W/保管監査と復旧前証拠を保全。Aを新しい隔離先へ復旧し、Wまでの全イベント/予約/取消を照合する。WをAの古いheadへ合わせてはいけない。Aが追い付くまでCLOSEDとし、未完了intentと中断/出力結果を照合する。整合性回復承認、新epoch発行、新policyの個別承認、運用再開は分ける。

W消失/rollback疑い、署名鍵喪失、登録系統不明の場合は停止。古いWバックアップを「最新」とみなさない。改変保護保管、独立した最新receipt、管理者の復旧証拠を照合し、証明できなければ再開しない。代表の再承認だけで履歴不明を無視しない。

A/W/登録root/管理資格が同時に侵害・巻き戻しされた場合を完全に防ぐ保証はできない。代表一人が全管理権限を保持する場合、accountを分けただけでは悪意ある管理者に対する独立性を主張しない。誰が監査保管・復旧を管理するかは代表確認事項である。

## 5. 鍵・代表本人確認

外部署名鍵は管理された鍵保管で非公開とし、PCは検証鍵/信頼rootだけを保持。PC機器のclient認証鍵はWindowsの専用サービスだけが利用し、外部署名権限と分ける。管理者向けbreak-glassは通常サービスから利用不可とし、使用時は停止・監査・再確認を必須にする。

代表操作はアプリのrole cookieだけで許可しない。本人確認基盤での再認証/MFA、subject/issuer/audience、nonce、承認対象scope/期限/目的版のdigest、操作IDを検証する。旧assertionを別事業・別期間・新世代へ流用させない。実装時には検証済み入力のcopy/正規化、サイズ制限、署名algorithmの固定、失効/鍵更新を含める。

AI04は代表のassertionがあっても内部会計不可。通常の役職/担当/active/task/事業/期間認可を残す。代表本人確認の成功を「全AIへ権限付与」と扱わない。

## 6. オフラインと送信情報

回線断、外部障害、head不一致、未完了確認、鍵/本人確認不明は会計取得・新規引き渡しを拒否。既存予約は消さず、必要なら停止未完了を維持する。復旧時も新規確認が必要。オフライン会計を許す仕様は今回採用しない。非会計業務は別認可で継続する設計だが、DB自体が未検証なら業務書込も再開しない。

送信候補は、不透明な組織/機器/事業/社員/task/policy/delivery参照、epoch/seq/head、固定action、scope/証明のdigest、nonce、承認subject参照、必要な期限/時刻のみ。会計値・顧客名・自由文・添付・銀行情報・ローカルpath・認証秘密を送らない。低エントロピーの会計金額をhash化して送る方法も使わない。識別子/digestも機密として保護し、送信/保管/保持期間を別承認する。

## 7. 費用と運用負担の見通し

今回は外部照会を禁止されているため、価格表・無料枠・契約条件を照会していない。確定月額/通貨見積は未算定。無料で運用できる前提は置かない。

仮の容量モデル：月3,000件の会計引き渡し、1件当たり全外部API要求8〜12回なら24,000〜36,000要求/月＋policy/停止/監視/認証要求。1更新のメタデータ2KiBなら、全要求を1記録と仮定した論理量は約47〜70MiB/月。これは測定値でも見積料金でもなく、複製/索引/暗号化/保管保持/backupの増分も含まない。実装確定後に要求数を再計測する。

費用式は、API/DB固定費＋要求数×要求単価＋GB月×保管単価＋witness/監査保管＋鍵/ID/MFA＋監視/backup/通信＋保守で比較する。小容量でも固定費・認証・運用工数が主になる可能性がある。Windowsサービス配備、権限設定、本人確認、独立管理、鍵/PC交換、停止時の対応担当を含めて見積もる。

次段階で代表がprovider/リージョン/冗長化/保持期間/認証方式と月額上限を指定し、最新料金と契約条件を確認してから採用を決める。サービス契約・資源作成は今回していない。
