# 会計タスク報告UI・未分類資料の管理設計

設計のみ。新UI、資料分類台帳、既存資料の書換え/削除、権限適用は今回実装しません。

## 未分類資料

対象にはartifacts.content、portfolio_documents.body、portfolio_reports.body、workflow/seminarの下書き・結果・履歴、learningへの複製、添付/媒体、利用者の手作業コピー等があります。DB外のローカルファイルも別の確認対象です。現在のタスク分類マーカーだけで過去資料の機密性を判定しません。

最初の棚卸しは代表が承認した範囲で読み取りだけを行い、ID・資料種別・事業・保存先・版・内容ハッシュ・作成者・複製元のメタデータをローカルに記録する案です。本文や会計値を汎用ログ・チャット・外部APIへ送信しません。自動推定は代表確認の候補に留め、分類確定・公開・削除に使いません。

将来の分類台帳は既存資料と別に保持し、資料ID/事業/版ハッシュ、分類（未確認・会計明細・限定集計・個人情報・公開可等）、確認者、確認日時、有効範囲、親資料参照を管理する案です。既存資料の本文は維持します。分類台帳自体もアクセス制限します。

- 未確認/ハッシュ不一致の資料は新しいAI配信経路で拒否。代表のローカル確認は別の認証経路。
- AI04を含む会計不要社員は、会計分類の本文・添付・プレビュー・検索抜粋を受け取れない。
- 添付の名前・URL・検索結果・エクスポート・履歴も同じ判定を通す。本文だけを隠してURLが残る方式は不可。
- 複製/要約/引き継ぎは親の機密分類と事業範囲を継承し、任意に低い分類へ変更しない。集計化して別の区分へ公開する場合は独立した代表確認と新しい参照を作る。
- 手作業で別タスクやファイルへコピーすると現在のマーカーは伝搬しない。確認された業務フローを専用経路へ統一し、AIにDB/ファイル/代表資格情報を渡さない。既存の全経路が保護済みとは報告しない。
- 任意SQLによるcross-business結合、自由文へ会計値を埋め込む運用は承認済みビューの代わりにならない。

未知資料拒否を既存の全汎用閲覧へ接続すると非会計業務も止まり得ます。対象画面・配信/検索/添付経路ごとに影響一覧と代表承認を用意し、一括の自動分類/削除/権限書換えはしません。

## 少数件集計・差分推測

候補対策は、承認された月次等の固定期間、許可された集計軸、最小母数、少数/補集合の抑制、重複・隣接期間の問い合わせ制限です。母数や閾値は業務目的とデータ量を見て代表が承認します。AIに件別識別子や自由なフィルターを渡しません。

単純に合計だけを見せても、1件の事業や既知の取引との差分で明細を推測できます。氏名削除や「集計」というラベルだけで匿名性を保証しません。問い合わせ履歴の制限には、社員・事業・期間・集計軸単位の専用記録が必要です。値そのものを一般ログへ残さず、抑制応答の差異も検証します。これらは今回未実装で、実データに対する秘匿性の保証は未確認です。

## 代表向け報告UI

### 一覧

代表認証を確認し、タスクID、事業ID、担当ID、進捗/待ち理由、対象期間、参照ID、申請/承認/失効状態、版、最終確認時刻を表示する案です。金額、本文、証憑、顧客名、添付URLを一覧/通知/汎用履歴へ含めません。メタデータも他事業/一般社員へ漏らさず、AI用と代表用の一覧を分離します。

`acct_task_reads.policy_id`は最初の取得マーカーであり、一覧の「現在の承認済みポリシー」に使いません。task_policies、現在のポリシー、期限・担当・状態を都度照合します。複数有効なら曖昧として拒否表示にします。スキーマや参照がなければ「未準備」とし、自動作成しません。

### 詳細・参照

詳細表示は専用参照IDだけをサーバーへ渡し、タスク/事業/社員/区分/項目/期間/代表承認/期限を毎回再検査します。認可後に限定データを取得してHTMLエスケープし、CSP/no-storeを維持します。拒否/失効/期限切れ時に古いキャッシュ・旧レスポンス・一般添付へ戻しません。

AI27の明細、AI28の監査はそれぞれ専用区分で扱い、別の社員が参照IDを知っても取得できないよう受領側も確認します。監査の事業/期間/項目だけでなく、伝票単位の範囲が必要ならその追加設計を先に承認します。現状は旧台帳の日付・収支区分・金額だけです。

### 提出・承認・完了

将来の専用報告レコードは、本文のコピーではなくtask/business、参照ID、許可区分・項目・期間、ポリシー/資料版の指紋、状態、提出者、承認者/時刻を保持する案です。既存の汎用artifactsには書きません。進捗は固定の状態コードで表し、自由文へ値を埋め込ませません。

提出→代表確認→承認/差戻し→完了は分け、POST・CSRF・現在の代表認証、状態条件付きUPDATE、更新件数確認、同一トランザクションの監査を必須にします。会計ポリシーの承認と報告内容の最終承認は別の記録です。報告承認から支払い・記帳・配信は起動しません。

現在のAccountingAccessはcompletedのタスクを拒否します。合成テストでも既存参照IDを完了後に使えないことを確認しました。そのため「完了しても同じIDでいつでも結果を表示する」UIは現在のサービスをそのまま使って実現できません。

候補は、確認中は専用報告状態を使い元タスクを参照可能な状態に保ち、完了後の数値再確認には代表が新しい確認タスクと現在有効なポリシーを明示的に用意する方式です。完了済みタスクの復活や恒久的な権限バイパスはしません。代替として履歴専用の認可コンテキストを設計する場合も、代表/AIの経路を分離し、期限と失効が効くことを検証して別承認を得ます。どちらを採るかは未確定で、UI実装前の代表確認事項です。

### 検証計画

- 一覧/通知/ログに金額・機密本文・添付URLが含まれない。
- 別の事業/社員の参照ID、期限切れ/失効後、重複ポリシー、完了済みタスク、版差替えを拒否する。
- ブラウザー戻る/キャッシュ/検索/エクスポート/印刷の情報残存を確認する。
- 同時承認/差戻し/失効を2接続で検証し、古い要求で承認が復活しない。
- 代表の全体確認・最終承認と、一般社員の非会計業務を回帰確認する。
- AIの参照に代表セッションを貸与せず、タスク実行者の認証・信頼境界を確認する。

今回の追加合成テストでは、既存の専用参照に本文を持たないこと、閲覧時に失効を再検査すること、completedを拒否することまで確認します。上記UI・分類・問い合わせ秘匿対策そのものの実装/ブラウザ検証完了を意味しません。
