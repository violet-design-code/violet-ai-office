# 第17段階：事業別案内・問い合わせ・面談導線

## 画面と動作範囲

既存ローカル起動後、代表で `http://127.0.0.1:8765/customer-journey` を開く。新しい「事業別案内・導線」メニューから、権限のある既存事業を選択できる。事業ID・名称・提供状態・価格を自動変更しない。ベネシード関連、セルフホワイトニング、スマホ教室（タブレット対応範囲は代表確認）、健康・美容商品等は既存の事業単位を使用し、未登録の事業を勝手に追加・統合しない。

1. 代表が紹介下書きを登録する。由来を「未確認」「VIOLET独自」「ベネシード公式事業に関連」から選び、商品/サービス、提供資格・営業権限、価格、参加/利用条件、法的分類、報酬、年齢条件の適用範囲を別々に記録。
2. 出典ID、公開HTTPS資料URL、確認日、再確認期限、確認内容、原文確認状態を記録する。自動取得・自動検証ではなく代表による原資料確認の申告。
3. 出典が未確認・取得不可・期限切れ、本文が未記入/要確認、由来未確認なら承認できない。ベネシード関連は指定の公式2ページに加え、契約等の別資料も必要。ページ名だけでVIOLETの資格や20歳以上の社会人という条件の適用範囲を確定しない。契約の法的分類・報酬体系を隠さず、必要な表示を人間が確認する。
4. 代表が現在版を明示承認しても、内部参照用にとどまり外部公開しない。原文未取得の公式情報は現時点では案内へ反映しない。
5. 本人が希望した関心と問い合わせを管理者が受付。既存の事業別顧客を選ぶか、新しい顧客を登録できる。新規顧客に連絡同意を自動付与しない。既存の営業・顧客画面で目的別同意/撤回・連絡停止を記録する。
6. 同意と現行担当権限が揃った場合だけ、必要な既存AIへ内部タスクを作る。実行・停止・優先度/担当変更・成果確認は既存の業務・営業支援画面を使う。
7. 本人希望と日程同意に基づき個別面談候補を登録。登録しただけでは確定しない。既存営業画面で現在条件と見積/税設定を確認し、代表が予約操作を承認後、別操作でモック検証する。本版は外部カレンダーを操作しない。
8. フォロー案は連絡同意と別のfollowup同意が必要。実送信は追加していない。

フォームは認証済み代表/許可された事業担当による受付補助であり、本人がインターネットから直接申し込む公開フォームではない。問い合わせ内容・連絡先・顧客情報を外部AIへ送信しない。

## データ設計・既存資産

追加型・再適用可能な版17は6表のみ。

| 表 | 用途 |
|---|---|
| cj_profiles | 事業別紹介・由来・版・代表承認 |
| cj_sources | 事業別出典・確認日・期限・状態・版 |
| cj_cases | 既存SCM案件との関連・本人の関心・受付キー |
| cj_routes | 既存内部タスクとの関連・選定理由・履歴 |
| cj_requests | 既存面談候補との関連・重複防止キー |
| cj_work_inputs | 参照した紹介情報の指紋と出典ID/版の記録 |

顧客・同意・営業案件・予約・タスク・成果物は既存のportfolio/scm/wf/tasksを再利用し、二重台帳を作らない。複合FKと全クエリの事業条件で境界を維持。同一受付キーの再処理は同じ案件を返し、本文が変われば競合として拒否。面談候補もキーと内容を照合して重複作成を防ぐ。実績とmockは既存の測定モードで分離し、模擬予約から売上・契約を作らない。

既存LINE本体は別リポジトリ。今回変更していない。本リポジトリの同意・停止・再同意・予約停止のモックと既存テストを再利用する。実LINE登録者を新しい事業顧客へ自動コピーしない。

## 権限・承認・品質

- サーバーは利用者の現行DBロールと事業ACLを検証する。表示非表示だけで保護しない。
- AI割当は第15段階の多対多割当を再利用。旧事業の互換運用でも本導線は明示的なwork権限を必須とする。全体管理者の権限をAIへ継承しない。設定・社員数・権限の自動変更はしない。
- 同意・停止・担当失効をタスク作成時だけでなく実行・承認時にも確認する。独立レビュー担当も明示的な事業割当が必要（AI28の既存レビュー担当はAI25であり、未割当なら承認待ちで停止）。既存営業画面から作る関連タスクでも確認する。
- 出典改訂や紹介改訂で紹介承認を解除する。営業操作の承認指紋にも紹介/出典の現在版を含めるため、条件を再承認しても古い送信・予約承認は復活しない。出典期限切れも実行時に拒否。
- 内部タスクは固定テンプレート・ルールで、LLM生成と表示しない。承認済み紹介だけを下書きへ反映し、未確認なら本文を作らず確認事項を返す。参照版変更後の古い成果物を承認しない。
- 取消・返金は紹介未確認という理由だけで妨げない。既存の代表承認・会計整合条件は維持。
- 秘密値入力、命令混入、一部の明白な健康/収益保証を拒否し、全出力をエスケープ。自動ルールは万能な個人情報検出・法令適合判断ではなく、AI28の内部確認案と人間による原資料・表現確認が必要。
- 設定変更・受付・割当は既存bf_events、アクセス拒否はops_auditと既存Web監査へ記録。POST拒否はロールバック後にも記録する。顧客本文を監査ログに複製せず参照ID/指紋を使う。
- 複数事業の顧客関連付けは既存の代表本人確認・両事業のidentity_link同意・権限付き操作のみ。氏名や連絡先一致で統合しない。SQLiteファイルへのOSアクセスは別途保護が必要。

## 移行・復旧

実DBは本作業では開いていない。Office起動で版17を適用するため、既存実DBを新コードへ向ける前には代表承認とバックアップ・復元コピーでの検証が必要。

1. [既存運用手順](runbook.md)で移行前バックアップを取り、元ファイルと旧コードを保存。
2. `python3 -m violet_office.ops restore --db BACKUP --output NEW_COPY` とhealthで新しい復元ファイルを確認。
3. 新コードをコピーで起動し、旧行保持・事業別導線・版17を検証。再適用しても旧行を変更しない。
4. 復元時は従来どおり割当/自動処理を停止し、紹介承認もpendingへ戻す。受付・出典・営業履歴は保持。自動再開しない。
5. ロールバックは旧コードと移行前バックアップの別コピーを使用。新DBから表を削除するダウングレードはしない。切替後の差分は人間が監査記録で照合する。

## 未実装・残る制限

公開顧客サイト、本人のWeb認証付き問い合わせフォーム、実LINE/メール送信、外部カレンダー・決済・LLMは未接続。公式原文取得・法令/契約確認とVIOLETの提供資格検証は未完了。プロフィール承認は人間による確認申告であり、公式機関による資格認証ではない。

予約確定は既存SCMの見積・税条件を継承し、見積不要の面談を独立して確定する専用経路は追加していない。紹介改訂で失効した内部成果物は再承認できず、必要なら既存ワークフローで新しい確認タスクを作る（自動再生成は未実装）。第20段階の完成版事業追加・担当割当画面と、第18段階の開発は行っていない。

PCはloopbackの既存起動で開ける。390px幅はブラウザ開発者ツールで確認可能。iPhone実機接続のために無認証公開・loopback制限解除を行わない。保護ネットワーク/HTTPS等の設計は別途必要。
